  "index_patterns": ["logs-my_app-prod"],
  "data_stream": { },

## Searching Data

### Write and execute a search query for terms and/or phrases in one or more fields of an index.

Q13: You want to find all documents in the `products` index where the `description` field contains the exact phrase "new and improved" OR the `name` field contains the term "ultimate". Which query should you use?

A)
GET /products/_search
{
  "query": {
    "bool": {
      "should": [
        { "match_phrase": { "description": "new and improved" } },
        { "match": { "name": "ultimate" } }
      ],
      "minimum_should_match": 1
    }
  }
}

B)
GET /products/_search
{
  "query": {
    "multi_match": {
      "query": "new and improved ultimate",
      "fields": ["description", "name"],
      "type": "phrase_prefix"
    }
  }
}

C)
GET /products/_search
{
  "query": {
    "query_string": {
      "query": "(description:\"new and improved\") OR (name:ultimate)"
    }
  }
}

D)
GET /products/_search
{
  "query": {
    "simple_query_string": {
      "query": "\"new and improved\" | ultimate",
      "fields": ["description", "name"]
    }
  }
}

Answer: A (While C and D could also work, A is the most precise and common way to structure this type of query with distinct conditions for different fields and match types)

### Implement pagination of the results of a search query.

### Diagnose shard issues and repair a cluster's health.

Q46: Your cluster health is yellow. Using `GET _cluster/allocation/explain`, you find an unassigned replica shard. The explanation indicates "cannot allocate replica on the same node as primary". What is the most likely cause and a valid first step to resolve this if you have other available nodes?

A) Cause: Insufficient disk space on other nodes. Step: Add more nodes to the cluster.
B) Cause: The primary shard's node is the only node in the cluster. Step: Add at least one more data node to the cluster.
C) Cause: `cluster.routing.allocation.same_shard.host` is set to `true`. Step: Set `cluster.routing.allocation.same_shard.host` to `false`.
D) Cause: The index setting `index.routing.allocation.include._name` is preventing allocation on other nodes. Step: Remove the restrictive index setting.

Answer: B (If there's only one node, a replica cannot be placed on a different node. Adding another node is the direct solution. C refers to a setting that prevents a primary and its replica from being on the same host, which is default and desired behavior, not the cause of this specific message if other nodes *were* available but different.)

Q47: The Cluster Allocation Explain API (`GET _cluster/allocation/explain`) returns a decision: `NO_VALID_SHARD_COPY`. What does this generally indicate as the primary reason for an unassigned shard?

A) The cluster has too many shards, and some need to be deleted.
B) None of the existing copies of the shard data (primary or replica) can be found or are healthy enough to be promoted to primary.
C) There are no eligible nodes to host the shard based on allocation deciders (e.g., disk watermark, attribute filtering).
D) The shard is currently being relocated to another node.

Answer: B (This decision means that Elasticsearch cannot find a valid, up-to-date copy of the shard data on any node to use as the primary shard. This is a more severe data availability issue than C, which is about node eligibility for a *new* copy.)
